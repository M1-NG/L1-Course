# 行为准则

本准则适用于写代码、写文档、查资料和做表格，可以和项目自己的说明配合使用。默认以谨慎为先，特别琐碎的小任务可以酌情简化流程。

## 通用工作原则

### 想清楚再写

- 动手前说明关键假设。如果需求有多种合理理解，列出这些理解，讲清取舍。
- 遇到不确定的地方，先停下来，说清楚卡在哪里，再向用户确认。
- 有更简单的做法就直接提出。有理由反对时，说明原因。

### 简单优先

- 只做用户要求的功能，不额外增加灵活性或可配置项。
- 一次性的任务不搭通用框架，也不用为不可能发生的情况提前设计。
- 交付前想一想，资深同行会不会觉得方案过度复杂？如果会，就简化到刚好够用。

### 控制改动范围

- 每一处改动都应能直接追溯到用户需求。沿用原有风格，避免顺手调整无关内容、格式或运行正常的代码。
- 清理本次改动产生的多余内容。原本就有的无关内容可以指出，由用户决定是否删除。

### 先定目标，再验证

动手前把需求写成可以核对的完成标准。多步任务先给出简短计划，为每一步列出验证点。标准应具体到能据此自行判断任务是否完成。

| 任务 | 可验证的完成标准示例 |
| --- | --- |
| 整理资料 | 按“是什么、做什么、怎么做”三个维度分类，每条整理结果附一句出处说明。 |
| 添加校验 | 先写覆盖非法输入的测试，再实现校验并让测试通过。 |
| 修复 bug | 先写能复现问题的测试，再修复代码并让测试通过。 |

复盘时，看看多余的改动是否减少，因过度复杂造成的返工是否减少，以及该问的问题是否在动手前问清楚了。

## C 语言编码规范

### 变量与结构体

变量、结构体的声明放在对应的头文件中。尽量避免创建全局变量或数组。

使用变量时逐项检查以下六点。

1. 每个变量只承担一个用途，含义不随流程阶段改变。
2. 先初始化再使用，检查所有分支是否都在使用前完成了赋值。
3. 完整初始化结构体成员，特别留意指针、状态、计数和位域。
4. 避免同名遮蔽，防止局部变量意外遮蔽全局变量或对象成员。
5. 降低全局耦合。模块私有数据尽量在文件作用域用 `static` 声明，通过 API 读写。
6. 跨模块使用数据前，确认初始化顺序、模块间的依赖关系，以及并发访问时的互斥要求。

### 排版

- 每级缩进 4 个空格，用空格对齐，不使用 TAB。
- 大括号 `{` 和 `}` 各占一行，与对应语句左对齐。
- `if`、`for`、`while`、`do` 的执行部分即使只有一条语句，也使用大括号。
- 一行一条语句。在独立代码块之间、变量声明之后合理留空行。
- 不留行尾空格，避免无意义的连续空行。
- 长语句通常在低优先级操作符处换行，续行保持清楚的缩进。
- 双目操作符前后合理留空格。`->` 和 `.` 两侧不加空格，关键字与后面的 `(` 之间加空格。

### 注释

- 注释统一使用中文，编码与所在文件一致。重点解释这样做的原因和限制，避免复述明显的代码动作。
- 保留已有函数注释的原文。在结构体或枚举中新增成员时，沿用该结构体或枚举已有的注释风格。
- 函数注释使用 Doxygen 风格，只写在函数定义处。头文件等处的函数声明不写函数注释。
- 其他注释使用 C 语言的单行注释。

```c
/**
 * @brief 计算两个整数的和。
 * @param a 第一个整数。
 * @param b 第二个整数。
 * @return 两个整数的和。
 */
```

## Git 提交与编译

### 开发阶段提交

- 开发阶段的提交使用 `WIP` 标记，方便后续把多个 WIP 提交合并成一条记录。
- 如果改的是上一次提交的代码，使用 `git commit --amend` 更新该提交。
- 提交后，在 `\\192.168.88.5\yaoming\workspace\` 下找到对应目录，执行 Git 同步并编译。

### 正式提交

使用 Git 全局模板目录中的提交模板，按本次改动的类型填写相应字段。

#### 【标题】

| 提交类型 | 标题格式 |
| --- | --- |
| TAPD 缺陷单 | `修复：【问题单号】问题标题` |
| 需求开发 | `新增：【需求单号】需求内容` |
| 代码或脚本优化 | `优化：【代码优化】优化的内容` |

#### 【问题原因】与【解决方案】

| 提交类型 | 【问题原因】填写内容 | 【解决方案】填写内容 |
| --- | --- | --- |
| TAPD 缺陷单、自测问题 | 问题的原因 | 问题的解决方法 |
| 需求开发 | 需求背景 | 需求实现方案 |
| 代码优化 | 优化的原因 | 优化的方法 |

#### 【测试建议】（可选）

有具体建议时再填写。说明哪些功能可能受影响、什么条件下容易出现问题，以及是否影响性能或内存。可按需填写以下内容。

| 项目 | 填写内容 |
| --- | --- |
| 核心功能 | 列出本次主要修改的业务，如 TPIC、低码率或 4G 保活。 |
| 影响功能 | 列出所有可能受影响的功能。例如，码率变化可能改变 SD 卡写入频次，进而影响功耗，测试时需关注写入频次和功耗。 |
| 特殊条件 | 列出复现或验证所需的环境和数据，如高并发、特定状态的数据、边界数据或低温数据。 |
| 性能/安全 | 说明是否需要压力测试或安全扫描。 |
